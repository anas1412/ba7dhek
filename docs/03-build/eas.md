# EAS: builds, updates, submission

Plan limits, fees and store rules here were checked on 2026-11-13 and are in [verified-facts.md](../05-reference/verified-facts.md). The mechanics of profiles, channels and runtime versions are from general knowledge of the tool; check each command against the EAS docs when first running it.

**Android first.** iOS profiles are defined from the start but not used until the Android pilot works.

## Why EAS
- Builds Android and iOS binaries in the cloud. iOS builds do not need a Mac.
- Manages signing credentials.
- Ships JavaScript-only fixes over the air, without a store review.

## Build profiles
Defined in `eas.json`.

| Profile | Purpose | Distribution | Backend |
|---|---|---|---|
| `development` | Day-to-day coding. Includes the dev client, so native modules (Google sign-in, maps, push) work. | Internal, installed directly on the developer's phones | Convex dev |
| `preview` | Testers. A release build, not on the public store. | Internal: APK for Android, TestFlight or ad hoc for iOS | Convex production |
| `production` | The store release. | Google Play and App Store | Convex production |

Each profile sets its own environment variables: Convex URL and Clerk publishable key.

## When a new build is needed
- A native dependency is added or upgraded.
- App config changes: permissions, icons, splash, bundle identifiers.
- The Expo SDK is upgraded.

Everything else is a JavaScript change and can go out as an update.

## EAS Update
- One channel per profile: `development`, `preview`, `production`.
- A JavaScript-only fix is published to a channel and picked up by installed builds on next launch.
- An update only reaches builds with a matching runtime version. Use a runtime version policy tied to the native code, so an update can never land on a build that lacks a native module it needs.
- Locale file changes are JavaScript, so a translation fix can ship as an update.

## Identifiers
To be fixed before the first build, because changing them later means a new app listing:

- **Android package name** and **iOS bundle identifier:** `tn.ba7dhek.app`, matching the domain `ba7dhek.tn`. Register the domain before the first build.
- **Scheme** for deep links: `ba7dhek`.

## Credentials
| Credential | Platform | How |
|---|---|---|
| Upload keystore | Android | Generated and stored by EAS |
| FCM V1 credentials | Android | From a Firebase project, which needs no payment method; uploaded to EAS for push |
| Google OAuth client IDs | Both | Three of them (iOS, Android, Web) from Google Cloud; configured in Clerk. See [auth.md](../02-architecture/auth.md) |
| Signing key fingerprints | Android | SHA-1 for the Google OAuth client, SHA-256 for Clerk's native application entry. Each build profile signs with its own key, so each needs registering |
| Distribution certificate and provisioning profile | iOS | Generated by EAS with the Apple Developer account |
| APNs key | iOS | Generated by EAS; used for push |

Secrets go in EAS environment variables or secrets, never in the repository.

## Accounts needed
- **Expo account:** the free plan gives up to 15 Android and 15 iOS builds a month at low priority, over-the-air updates for 1,000 monthly users, and store submission. It cannot incur overage charges.
- **Google Play Console:** 25 USD, one time. Tunisia is supported for registration.
- **Apple Developer Program:** 99 USD a year. Needed for any iOS build installed on a phone through EAS, for push credentials, and for Sign in with Apple.
- How these are paid from Tunisia: [tunisia-constraints.md](../04-launch/tunisia-constraints.md).

## Living within 15 builds a month
- Batch native changes. Adding a native library, changing permissions or icons each force a build; do several at once.
- Everything else goes out as an update.
- Two build profiles in regular use on Android (`development` and `preview`) means about seven rounds a month.

## Submission
- **Android:** EAS Submit uploads to the internal testing track, then the closed track. A personal account created after 13 November 2023 must keep at least 12 testers opted in for 14 consecutive days before applying for production access. Plan for it: see [store-readiness.md](../04-launch/store-readiness.md).
- **iOS:** EAS Submit uploads to TestFlight. External testers need a beta review.

## iOS without a Mac
- EAS builds iOS in the cloud, so no Mac is needed to produce a build.
- Installing that build on an iPhone needs the paid account. The only way around it is a local build, which needs a Mac.
- Push can be tested on an iOS simulator, which also needs a Mac. Without one, iOS push is tested on a real iPhone with the paid account.

## Routine
1. Code against the `development` build.
2. When a milestone is done, cut a `preview` build and send it to testers.
3. Small fixes go to the `preview` channel as updates.
4. For release, cut a `production` build from the same commit that testers approved, and submit.

## Versioning
- `version` in app config is the user-visible version: `0.1.0` for the first tester build.
- Build numbers increment automatically through EAS.

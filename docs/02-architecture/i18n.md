# Languages and right-to-left

**Rule: the app ships in Arabic, French and English from the first screen.** This is a founding requirement, not a later feature. No user-facing string is ever hard-coded.

## Locales
| Code | Language | Direction |
|---|---|---|
| `ar` | Arabic | Right to left |
| `fr` | French | Left to right |
| `en` | English | Left to right |

- **Default:** the device or browser language if it is one of the three. Otherwise Arabic for a device in Tunisia (region `TN` or time zone `Africa/Tunis`), and French elsewhere.
- **Changing it:** Settings → Language. The choice is stored on the device and on the user row.
- **Arabic register:** Tunisian dialect (Derja), written in Arabic script. Decided 2026-11-13. See "Writing the Arabic" below.

## Libraries
- `expo-localization` to read the device locale: `getLocales()` returns the user's locales in order of preference, each with a `languageCode` and a `textDirection` (verified).
- `i18next` with `react-i18next` for translation, plurals and interpolation. Expo's own guide uses a different library, i18n-js, and lists i18next as a maintained alternative (verified). i18next is chosen for its plural handling.
- `@formatjs/intl-pluralrules` and `@formatjs/intl-relativetimeformat` as polyfills, loaded before i18next starts.

**Why the polyfills.** i18next supports Arabic's six plural forms through key suffixes (`_zero`, `_one`, `_two`, `_few`, `_many`, `_other`) but depends on `Intl.PluralRules`, and since version 24 has no fallback without it. React Native's engine, Hermes, lists `PluralRules` and `RelativeTimeFormat` as planned, not done; sources disagree on whether `PluralRules` has landed (all verified). Shipping the polyfills removes the doubt.

**Other gaps in Hermes' `Intl` (verified).** On iOS, `NumberFormat` lacks compact notation and `formatToParts`. The formatters in `src/lib` must avoid those features.

## File layout
```
src/i18n/
  index.ts          initialises i18next, picks the locale
  locales/
    ar.json
    fr.json
    en.json
```

- One file per language, with the same keys in each.
- Keys are grouped by screen: `jobs.card.distance`, `onboarding.radius.title`.
- English is written first and is the reference; the other two must have every key.

## Rules for writing strings
- No string concatenation. Use interpolation: `"{{count}} jobs near you"`.
- Use the plural forms i18next provides. Arabic has six plural categories; French and English have two.
- No text inside images.
- Format numbers, dates and relative times with the `Intl` APIs and the active locale, never by hand.
- Distances: one formatter, taking metres and returning localised text.
- Pay: one formatter, taking amount and period. The currency is Tunisian dinar.

**Digits.** Western digits (0 to 9) in all three languages. In the Unicode locale data, `ar-TN` defaults to Western digits, while `ar-EG` defaults to Arabic-Indic ones (verified). On a phone the result depends on the device's own locale data, so the formatters pin it explicitly with the locale `ar-TN-u-nu-latn`. Check the output on a real device.

## Writing the Arabic
The Arabic interface is in Tunisian dialect, the way people in Tunisia speak, not in formal standard Arabic.

- **Script:** Arabic letters, right to left. The Latin-with-digits spelling people use in chat ("ba7dhek") is for the brand name only, never for interface text.
- **Tone:** the same plain voice as the other two languages. Everyday words, no slang that only one region or age group uses.
- **Spelling:** Derja has no official spelling, so the app keeps a short word list of its own and uses it consistently. The list lives beside the locale files as `ar.glossary.md` and is started with the first screen.
- **Legal text:** the privacy notice and terms are written in standard Arabic and French, because those are the registers legal text is read in. The interface around them stays in dialect.
- **Who writes it:** a native speaker, by hand. Machine translation into Tunisian dialect is not reliable enough for interface text; this is a judgement, not a tested claim.
- **Locale code:** `ar` in the app's files, formatted with the `ar-TN` locale.

## Right-to-left layout
- Use logical properties everywhere: `start` and `end`, `marginStart`, `paddingEnd`. Never `left` and `right` for layout.
- React Native mirrors flex rows automatically when the app is in RTL mode.
- Icons that imply direction (back arrow, chevrons, send) must flip. Icons that do not (clock, pin) must not.
- Text alignment follows the language; do not force `textAlign: "left"`.

**Setup (verified).** Right-to-left support is on by default in current Expo. It is configured through the `expo-localization` config plugin (`supportsRTL`, `supportedLocales`), and on iOS the device language must be listed in `supportedLocales`.

**Switching direction at runtime (verified).** A direction change takes effect only after a restart: React Native's documentation says `forceRTL` "requires a full app restart to take effect". Expo's documented method is to call `I18nManager.allowRTL` and `I18nManager.forceRTL`, then `Updates.reloadAsync()` from `expo-updates`. So choosing or leaving Arabic in Settings shows "the app will reload" and reloads. Switching between French and English needs no reload.

This does not work in Expo Go, which resets the setting; another reason for development builds.

**Why keep a language switch in the app.** Expo notes that per-app language is a system setting, so a custom picker is often unnecessary. It stays here because many phones in Tunisia are set to French or English by people who would rather read Arabic, and the system setting is hard to find. That is a judgement, not a measured fact.

**The swipe gesture does not mirror.** Right means apply and left means pass in all three languages, because the gesture is a physical direction, not a reading direction. The two buttons under the stack carry icons and labels, so the meaning is never direction-only. This is a design decision to revisit after testing with Arabic readers.

## Fonts
One family that covers both Arabic and Latin script, so the three languages look like one product. The design system specifies it; see [the design docs](../06-design/design-system.md).

Arabic text needs more line height than Latin at the same size. Text styles define line height per script where needed.

## User-written content
- Job titles, descriptions, company names, "about" texts and chat messages are stored and shown exactly as written. They are not translated.
- A job written in French appears in French to an Arabic-language user.
- Text direction for user content is detected per string, so an Arabic job title renders right to left inside a French interface.

## Fixed lists
Job categories, contract types, company categories and report reasons are stored as keys (`hospitality`, `part_time`) and translated in the app.

## Server-side text
Push notifications are written by the server. See [push.md](push.md).

- The Convex code holds its own small catalogue for the three languages.
- Each user row has a `language`, updated whenever the app's language changes.

## Store listings
Google Play and the App Store both accept localised listings. Prepare the name, short description, full description and screenshots in all three languages.

## Checks before any release
1. Every key exists in all three locale files. A script compares them and fails the build on a gap.
2. Every screen is opened in Arabic and checked for mirroring, clipped text and unflipped icons.
3. Every screen is opened in French, which is usually the longest of the three, and checked for truncation.
4. A push is received in each language.

# Push delivery

What gets sent and when is in [notifications.md](../01-product/notifications.md). This file covers how. Sources for the verified points are in [verified-facts.md](../05-reference/verified-facts.md).

## Pieces
- **`expo-notifications`** in the app: asks permission, obtains the Expo push token, handles taps.
- **Convex Expo push component** (`@convex-dev/expo-push-notifications`): stores tokens and sends.
- **Expo Push Service:** relays to FCM on Android and APNs on iOS.

## What the component does (verified)
- `recordToken(ctx, { userId, pushToken })` stores a user's token.
- It batches calls to Expo's API. Each batch is a job in a work pool with a parallelism limit.
- Failed requests and temporary per-message failures are retried with exponential backoff.
- Each notification has a state: `awaiting_delivery`, `in_progress`, `delivered`, `failed` or `needs_retry`.
- Per-user pause and resume calls exist.
- An optional `EXPO_ACCESS_TOKEN` is supported for Expo's enhanced push security.

- Sending: `sendPushNotification(ctx, { userId, notification })`, where `notification` takes Expo's push message fields. `sendPushNotificationBatch` sends many at once.
- Removing a token: `removePushNotificationToken`, by user id.
- Registered in `convex/convex.config.ts` with `app.use(pushNotifications)`.

**One token per user.** The component's source updates the existing row for a user instead of adding one, so the last device to register is the only one that receives pushes. The README does not say this; it was read in the code. Accepted for the MVP: one person, one phone.

## What is not verified
- The README carries no stability label and shows no version.
- It does not mention Expo push receipts, so "delivered" appears to mean "accepted by Expo", not "arrived on the device".

## Token lifecycle
1. After the user grants permission, the app gets the Expo push token.
2. It calls the `push.register` mutation, which calls `recordToken` for the current user.
3. The app re-registers on every launch, since tokens can change.
4. On sign-out, the app calls `push.unregister`.
5. On account deletion, the server removes the token.

## Sending
All sends originate in Convex functions, never from the app.

| Trigger | Function | Timing |
|---|---|---|
| Job published | `notify.fanOutNewJob` | Scheduled right after the publish mutation |
| Application accepted | `notify.match` | Scheduled by `swipes.decide` |
| Message sent | `notify.message` | Scheduled by `messages.send` |
| Right swipe | `notify.applicants` | First one immediately; then at most hourly per job |
| Company approved | `notify.companyApproved` | Scheduled by the admin mutation |
| Morning digest | `notify.digest` | Daily scheduled job, for candidates on "digest" and for jobs held back by quiet hours |

Sends are scheduled rather than done inline so that the user's action returns at once and a push failure can never fail the action.

## Localisation
The server writes the notification text, so it needs the translations too.

- A small catalogue of push strings in Arabic, French and English lives in the Convex code.
- Each send looks up the recipient's `language` on their user row.
- Job titles and company names are inserted as the employer wrote them.

See [i18n.md](i18n.md).

## Payload
Every push carries a data object the app uses to route the tap:

- `type`: `new_job`, `match`, `message`, `applicants`, `company_approved`, `digest`
- the relevant id: `jobId` or `matchId`

Tapping opens the screen listed in [notifications.md](../01-product/notifications.md). If the app was closed, the route is applied after sign-in state has loaded.

## Caps and quiet hours
Enforced in `notify.fanOutNewJob`, using the `pushCounters` table:

1. Skip candidates whose setting is not "all".
2. Skip candidates at the daily cap.
3. Inside quiet hours, do not send; the morning digest picks the job up.
4. Otherwise send and increment the counter.

"Local time" means Tunisian time for everyone in the MVP; no per-user time zone.

## Platform setup
- **Android:** FCM V1 credentials uploaded to EAS. Firebase's free plan needs no payment method (verified).
- **iOS:** an APNs key generated by EAS. "A paid Apple Developer Account is required to generate credentials" (verified).
- Remote push is unavailable in Expo Go on Android from SDK 53; a development build is required (verified).
- iOS push can be tested on a physical device or on a simulator with Xcode 14 or later (verified). A simulator needs a Mac.
- Expo's push service is free, with a limit of 600 notifications a second per project (verified).
- The fan-out schedules work with `ctx.scheduler.runAfter`. One function can schedule up to 1,000 others (verified), so a large fan-out sends in batches through `sendPushNotificationBatch`, not one scheduled function per recipient.
- The morning digest is a cron job defined in `convex/crons.ts` (verified).

## Failure handling
- A token Expo reports as invalid is removed, so dead devices do not accumulate.
- The fan-out records how many candidates it targeted on the job, which gives the employer a number to see and gives a way to notice a silent failure.

## What is built (2026-11-14)

Backend, in `convex/notify.ts`, `convex/push.ts`, `convex/crons.ts` and `convex/lib/pushRules.ts` / `pushText.ts`. Covered by 20 tests; none of it has yet delivered a notification to a real phone.

| Function | What it does |
|---|---|
| `push.register` / `push.unregister` | Stores or removes the phone's Expo push address. Only the Expo address format is accepted |
| `push.setNewJobs` | A candidate's choice: each job, once a day, or never |
| `notify.newJob` | Fan-out on publish: candidates whose own radius covers the job, on "each job", under the cap of 5 a day, outside 22:00 to 07:00, with a registered phone |
| `notify.digest` | Daily at 06:00 UTC (07:00 in Tunisia): one push with a count. Overnight jobs for "each job", the last 24 hours for "once a day" |
| `notify.match` | The candidate is told an employer accepted them |
| `notify.message` | Runs 4 seconds after a message; skipped if the other side has read it by then. Pushes in one chat replace each other |
| `notify.applicant` / `notify.applicantsLater` | First applicant at once; after that at most one push an hour per job, with a count |
| `notify.companyApproved` | The owner is told the business was approved |

App, in `src/features/push/`:
- One screen explains what will be sent before the phone asks its own question. It is shown once; after that the choice lives in Settings.
- The phone registers on every launch when permission exists, and unregisters on sign-out.
- A tap opens the job, the applicants list, the chat, or the home screen.
- Three Android channels: new jobs, messages, applications and approvals.
- Settings shows whether this phone receives notifications and, for candidates, the new-job frequency.

**Differences from the plan above**
- The plan's names `notify.fanOutNewJob` and `notify.applicants` became `notify.newJob` and `notify.applicant`.
- "They are not currently in that chat" is approximated by the 4-second wait and the read mark. There is no live presence.
- Settings has the new-job frequency only. A switch per event type is not built.
- Tokens that Expo reports as invalid are not yet removed.
- The fan-out looks at the nearest 500 candidates and the digest reads every user row. Both are fine for one town and need paging beyond it.
- Nothing is measured yet (sent, opened, turned off).

## What Anas has to do before a phone receives anything

These need accounts and keys, so they are not done:

1. Create a Firebase project (free plan) and add an Android app with the package name `tn.ba7dhek.app`.
2. Download its `google-services.json` into the project root and add `"googleServicesFile": "./google-services.json"` under `android` in `app.json`.
3. Create a service-account key for Firebase Cloud Messaging (V1) and upload it with `eas credentials`. Expo's guide: https://docs.expo.dev/push-notifications/fcm-credentials/
4. Make a new development build. The notifications package is native, like the map and vibration added before it.

Without these the app runs as before: asking for the push address fails quietly and nothing is sent.
